# GitHub 개발 워크플로 

## 1. Issue 생성 — 작업 등록

- GitHub에서 앞으로 수행할 작업을 Issue로 등록한다.
- 작업 내용과 목적을 작성하고 **Label을 반드시 부착**한다.

**목적:** 누가 어떤 작업을 하는지 관리하기 위함.

## 2. 브랜치 구분 — 코드 관리

- **main:** 검증된 안정적인 코드 보관
- **dev:** 팀원들의 개발 코드를 통합하는 브랜치
- **개인 작업 브랜치:** 각자 기능을 개발하는 공간 (사용 여부는 팀 규칙 확인 필요)

**목적:** 개발 중인 코드가 안정적인 main에 직접 영향을 주지 않도록 분리.

## 3. dev Pull — 작업 전 최신화

- 개발 시작 전 원격 저장소의 최신 `dev` 코드를 가져온다.
- 개인 작업 브랜치를 사용한다면 최신 dev를 기준으로 작업을 시작한다.

**목적:** 다른 팀원이 변경한 내용을 반영하여 충돌을 줄이기 위함.

## 4. 개발 — 기능 구현

- 자신이 담당한 Issue에 맞춰 기능을 구현한다.
- 로컬에서 실행 및 정상 동작을 확인한다.

**목적:** 담당 기능을 구현하고 검증하기 위함.

## 5. Commit → PR → Merge — dev 통합

1. **Add:** 변경한 파일을 Commit 대상으로 등록
2. **Commit:** 변경 사항을 로컬 Git에 기록
3. **Push:** 작업한 코드를 GitHub에 업로드
4. **PR 생성:** `dev`에 코드를 합쳐 달라고 요청 (Label 부착)
5. **PR Review:** 다른 팀원이 변경 사항 검토
6. **Merge:** 검토된 코드를 `dev`에 통합
7. **Close:** PR 종료 및 Issue 종료

**목적:** 다른 사람의 검토를 거쳐 개발 코드를 안전하게 통합하기 위함.

※ Merge는 권한을 가진 사람이 수행하며, 구체적인 담당자는 팀에서 정해야 한다. Merge된 PR은 일반적으로 자동 종료된다.

## 6. 주 1회 dev → main 통합

- 매주 정해진 날짜에 파트별 `dev` 코드 검토
- 정상 동작과 문제 여부 확인
- `dev → main` PR 생성
- 리뷰 및 승인 후 Merge

**목적:** 개발 중인 코드 중 검증된 버전만 main에 반영하기 위함.

---

## 전체 흐름 요약

`Issue 생성 → 브랜치 관리 → dev 최신화 → 개발 → Add·Commit·Push → PR·Review·Merge(dev) → Issue 종료 → 주 1회 main 통합`

**핵심 원칙:** 개발은 분리해서 진행하고, 검토 후 dev에 통합하며, 검증된 코드를 주기적으로 main에 반영한다.

※ 원본 공지에는 개인 작업 브랜치의 사용 여부와 PR 승인·Merge 담당자가 구체적으로 명시되어 있지 않으므로 팀 내 확인이 필요하다.
